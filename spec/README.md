## Generated sections

Three chapters carry a header naming the engine commit they were produced from:

```text
<!-- generated by tools/generate.py from a8c2dce (2026-10-25); do not edit by hand -->
```

Those files are a **function of the reference implementation**. Editing them by hand is the
one change that cannot survive the next regeneration, so a wrong keyword, operator, error code
or stdlib signature is fixed in the engine or in the generator — never in the rendered chapter.

`sections` that are prose (00, 02, 03, 04) are authored and never touched by the generator.

## The pin

[`generated.json`](generated.json) records the commit and date the generated chapters were
produced from, plus the surface counts the generator reconciled: keywords, tokens, error codes,
stdlib modules and stdlib functions.

```console
$ python3 tools/check_drift.py --engine /path/to/tallowsphere
```

The checker separates two kinds of drift, because they need different verdicts:

- **Content drift** — keywords, tokens, error codes, modules or declarations changed and the
  spec was not regenerated. **Failure.** The published language surface now disagrees with the
  published engine.
- **Pin drift** — only `engine_sha` / `generated` differ, and the content is identical.
  **Warning.** The spec is behind; it is not wrong.

CI runs both: regenerating at the pinned commit must reproduce the tree byte for byte
(freshness), and regenerating against engine `main` must produce the same content (drift).

## Regenerating

```console
$ python3 tools/generate.py --engine /path/to/tallowsphere
$ git diff --stat        # anything unexpected here is the finding
```

Run it against a checkout of the engine at the commit you intend to pin, then update
`generated.json` in the same commit. A regeneration that changes prose is a generator bug, not
an editorial improvement.

## Changing the specification

A change to a normative sentence is a change to the language. Say which sentence, which
programs it affects, and what the conformance suite says afterwards:

1. Write the case that distinguishes the old reading from the new one.
2. Run the suite. If the change breaks a case, the case is the argument.
3. If it breaks none, the change is not yet observable — land the case first, or say plainly
   that the change is editorial.
